## V2.1 資料正確性

- 全歷史分頁讀取（500 筆／頁），移除先前只讀 90 天的限制；單頁失敗時不以不完整結果覆寫手機舊資料。
- 快速熱量輸入：`protein/fat/carbs=null` 表示未知，真正零值仍維持 0；當日總覽、餐別明細和歷史都有缺值警告。
- 飲食紀錄有 `nutrition_source` 欄位保留來源類型（legacy、quick_kcal、manual、scanned、ai_estimate 等）。
- 食品搜尋將正式食品與候選資料整合，缺值候選保留「待補」，不可當成完整營養食品直接記錄。
- `100ml` 和 `100g` 份量換算獨立處理。
- 監看同步狀態；離線紀錄排隊，網路恢復後走既有隊列上傳。

## V2.2 食品資料庫管理

- 私人待審核提交表、照片欄位、私有照片 Storage 桶。
- 照片可於掃碼建檔時提交；登入者只讀／寫自己的照片，管理員後端用短效簽名連結查看。
- 管理員權限在 `food_app_admins`，使用者無權自行新增管理員；不採用前端 user_metadata 判定。
- `food-admin` Edge Function 的 `status/list/review/link_photo/candidate_gaps/complete_candidate` 等動作需要 JWT；審核與寫正式食品另外核對服務端管理權限。
- 已有條碼需要管理員明確勾選允許合併，不能默默覆蓋資料。
- 營養完整及來源說明必填才可公開；候選商品必須輸入完整四項數值、官方 https 來源和審核備註才能轉成可記錄。
- 未知營養素不會被自動填 0，原先 351 筆候選數字保持不變，未取得完整官方資料不得宣稱「已補齊」。

## V2.3 健康趨勢、離線、跨裝置及資料權利

- 最近 7／30 天的已知熱量與蛋白質平均，以及未記錄、未知欄位的清楚標記。
- 私人 `food_weight_logs`：依日期記錄體重、更新或刪除、查看歷史。
- 私人 `food_user_state`：跨裝置常用食品、常吃組合及每日歷史目標同步。
- 帳號頁面可匯出 CSV 全部飲食明細、JSON 飲食／體重／目標／常用食品與套餐；CSV 已加公式前綴逃逸，避免開試算表執行公式。
- 帳號刪除需「刪除帳號」文字＋二次確認，再以登入本人 JWT 驗證，清除私有照片、未核准個人食品、相關個人資料。
- 食品份量確認改底部視窗，支援關閉按鈕／Esc；110% 原曾水平溢位，經 90～120% Chromium 測試修正。
- Service Worker 預存本機 App Shell 與固定版本 JS 供離線開啟，僅限白名單靜態資源；不快取 Supabase 使用者資料、Auth 或 AI 回應。
- 設定頁不再用卡片順序分組，未來增加卡片不會讓外觀和帳號設定互換。

## 已確認安全檢查

- 存取自己體重與雲端偏好皆啟用 RLS，匿名角色無表格讀取權。
- `public.rls_auto_enable()` SECURITY DEFINER 原允許匿名執行；現在已撤銷一般使用者與匿名執行權。
- Edge 管理功能只有服務端 `food_app_admins` 授權，不由前端信任管理員身分。
- `diet_logs` 和 `custom_foods` 加上必要索引。
- Supabase 安全提醒尚剩：`pg_net` 擴充功能位於 `public`，Auth 外洩密碼檢查未啟用；這些是後台設定／基礎設施層級，不在本次擅自重配擴充功能。

## 已知限制／避免錯誤宣稱

- 自動測試通過不等於已實測真 iOS 相機、推播、離線與雙機同步。
- 新資料目前用日期／先後寫入作跨裝置合併，離線兩台裝置同時修改相同常用食品，仍可能需要較細粒度的衝突協調。
- 兩階段的「發布共用食品＋標記審核」目前不是資料庫單一交易，服務端會留下可辨識錯誤訊息，極端網路失敗需管理員人工核對。
- 體重紀錄寫入目前需要網路，只有飲食記錄允許離線排隊。
- 憑證／行政帳號失效時需由 Supabase 專案維護者恢復管理員權限。
- 帳號刪除的破壞性流程無法對正式帳號做測試，請以專用帳號實測。
- 食品 AI 辨識屬輔助估算，不能作為醫療建議或正式官方營養證明。
